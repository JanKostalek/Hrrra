# Hrrra Technical Reference

This document is the technical map of the project. It is meant to answer questions like:

- where the game is loaded from,
- which files are the source of truth,
- how data is persisted locally and online,
- where each screen gets its assets,
- how profiles, highscores, shop, badges, mine, and Android work together,
- which code paths to inspect when something is rendered, unlocked, or saved.

The document is intentionally practical. It is organized by runtime layer and by feature, so you can jump to the part you need instead of reading the codebase from scratch.

## 1. Project Layers

The project has three important runtime layers:

- root source files
- the `www/` mirror used by the local file-based web build
- the Android packaged public mirror used inside the Capacitor app

### Root source

The root files are the editing source. This is where the canonical versions of the runtime files live:

- `index.html`
- `game.js`
- `style.css`
- `config.js`
- `tuning.js`
- `physics.js`
- `world.js`
- `player.js`
- `platform.js`
- `elevator.js`
- `version-info.js`
- `version.json`

The root also contains the project notes and workflow docs:

- `WORKFLOW.md`
- `CHANGES.md`
- `MECHANICS.md`
- `TESTER_INFO.md`
- `gfx2.md`
- `assets/LEVEL_ASSETS.md`

### `www/`

`www/` is the browser-facing build mirror. It is used by the local `file:///.../www/index.html` path and by the Capacitor web shell.

Important point:

- `www/` is not the editing source.
- when `www/` is older than root, the browser can show stale behavior.
- the mirror is generated by the copy script, not hand-edited as the primary source.

### Android public mirror

The Android app loads the web game from:

- `android/app/src/main/assets/public`

This directory must contain the same runtime files as the web build, including the version metadata, otherwise the app can report the wrong release information or show outdated behavior.

The sync model is script-driven.

### Copy scripts

The main sync script is:

- `scripts/copy-web-assets.js`

That script copies runtime files from the project root into:

- `www/`
- and, when called with `--android-public`, into `android/app/src/main/assets/public`

The script copies these runtime files:

- `future-release.html`
- `version.json`
- `version-info.js`

- `config.js`
- `tuning.js`
- `physics.js`

It also copies the runtime asset folders under `assets/`, including:

- `assets/gfx2`

- `assets/intro`
- `assets/level1`

There is also a native intro sync helper:

- `scripts/copy-intro-native-assets.js`

The important npm scripts are defined in `package.json`:

- `copy:web`
- `copy:intro:native`

The practical meaning is:

- `copy:web` refreshes `www/`
- `copy:web:android` refreshes the Android public mirror
- `cap:sync` does the combined sync for web, native intro assets, Capacitor, and Android public

## 4. Persistence Model

The game uses browser storage for local persistence.

### Active profile storage

The key concept is the active player profile.

Important storage keys in `game.js`:

- `hrrra_player_name_v1`
- `hrrra_player_id_v1`
- `hrrra_badge_stats_v2_<playerId>`
- `hrrra_economy_v2_<playerId>`
- `hrrra_player_skin_progress_v2_<playerId>`
- `hrrra_max_score_v3_<playerId>_<difficulty>_<mode>`

There are also legacy keys that can be migrated:

- `hrrra_badge_stats_v1`
- `hrrra_economy_v1`
- `hrrra_player_skin_progress_v1`
- `hrrra_max_score_v2_...`

### Profile switching

The profile switch flow is centered on:

- `switchPlayerSession(nextPlayerName, nextPlayerId, shouldPersistCurrentProfile)`

That function:

- persists the current authenticated profile if needed,
- stores the new player name and player id,
- switches the active profile storage scope,
- reloads the skin progress,
- refreshes profile-dependent UI.

Guest mode is created by:

- `continueAsGuest()`

Guest players get a generated `g_...` id and are treated as a separate local session.

### Migration behavior

Legacy storage migration is handled by:

- `migrateLegacyProfileStorageIfNeeded(playerId)`

This migration copies the old single-key progress data into the new per-player scoped keys, but only if the current player does not already have scoped profile data.

### What is persisted locally

The main persistent buckets are:

- badge stats
- economy stats
- skin progress
- per-mode max score
- player name / player id
- update banner seen version
- admin global config / admin per-level config

## 5. Online Backend

The game uses a Vercel-hosted backend for authentication and high scores.

### Base origin resolution

The online API origin is resolved in `game.js` by:

- `getOnlineApiBaseOrigin()`

Behavior:

- on normal HTTPS/HTTP hosting, it uses `window.location.origin`
- on localhost or file-based/offline contexts, it falls back to:
  - `https://hrrra.vercel.app`

### API endpoints

The runtime endpoints are:

- `ONLINE_HIGHSCORE_API_URL` -> `/api/highscore`
- `ONLINE_AUTH_API_URL` -> `/api/auth`

### Authentication endpoint

`api/auth.js` implements sign-in and registration.

Storage keys used on the backend:

- `hrrra:auth:account:<playerId>`
- `hrrra:auth:name:<playerName>`

The auth flow:

- normalizes name and password
- creates a new account when the name does not exist
- verifies the password when the name already exists
- returns `playerId` and canonical `name`

### High score endpoint

`api/highscore.js` stores leaderboards in Vercel KV.

Board keys:

- `hrrra:leaderboard:<board>:scores`
- `hrrra:leaderboard:<board>:top-scores`

Player metadata:

- `hrrra:leaderboard:player:<playerId>`

Allowed boards:

- `jump_easy`
- `jump_hard`
- `full_easy`
- `full_hard`

What the endpoint tracks:

- best score per player
- best run scores
- top 15 leaderboard entries
- best rank for the player
- current run rank

## 6. Android Layer

The Android app is a Capacitor shell around the same web runtime.

### Main activity

The Android entry activity is:

- `android/app/src/main/java/cz/hrrra/game/MainActivity.java`

It does the following:

- registers the custom plugins
- hides system bars
- clears WebView cache/history
- configures edge-to-edge window behavior
- optionally initializes ads

### Custom plugins

The app registers these custom native plugins:

- `PrivacyOptionsPlugin`
- `RewardedContinuePlugin`
- `MineStorageReminderPlugin`

### Mine reminder bridge

The mine reminder feature is implemented across:

- `MineStorageReminderPlugin.java`
- `MineStorageReminderWorker.java`

Current behavior:

- JS calls the plugin with a delay in milliseconds
- the plugin checks Android notification permission on Android 13+
- if permission is granted, it schedules a `WorkManager` one-time job
- the worker posts the reminder notification
- calling the sync method with `delayMs <= 0` cancels the reminder

The reminder notification currently uses:

- channel id: `mine_storage_reminder`
- notification id: `6106`

### Android manifest

The Android app manifest is in:

- `android/app/src/main/AndroidManifest.xml`

It declares:

- the main activity
- the splash activity
- internet permission
- notification permission

### Android public mirror

The Android packaged web files are copied into:

- `android/app/src/main/assets/public`

This mirror needs to stay in sync with root for:

- `game.js`
- `style.css`
- `index.html`
- version metadata
- runtime asset folders

## 10. What To Check When Something Is Wrong

If a screen does not show the expected asset, check in this order:

1. `index.html` for the DOM element
2. `game.js` for the renderer or resolver
3. `style.css` for layout and visibility
4. `assets/` for the actual file
5. `www/` or Android public mirror for stale copies

If a value does not persist, check:

1. the read/write pair in `game.js`
2. the storage key prefix
3. whether the current profile is authenticated or guest
4. whether the data was migrated from a legacy key

If a leaderboard or auth call fails, check:

1. `game.js` endpoint resolution
2. `api/auth.js`
3. `api/highscore.js`
4. the Vercel KV connection and allowed board id

## 12. Badge System

The badge system is centered on the `BADGE_SERIES` array in `game.js`.

### Categories

The badge categories are ordered by:

- `Single Run`
- `All Runs`
- `Skills`
- `Lifetime Legends`
- `Discovery`

Each category has its own short explanatory copy in `BADGE_CATEGORY_COPY`.

### How a badge series is shaped

Each series entry contains:

- `id`
- `category`
- `name`
- `description`
- `tiers`

Each tier contains:

- tier name such as `Bronze`, `Silver`, `Gold`, or `Legend`
- value text
- sprite key

### Important series groups

- `Single Run` badges track one run only
- `All Runs` badges track lifetime totals
- `Skills` badges track special mechanics or mastery goals
- `Lifetime Legends` badges are long-term milestone titles
- `Discovery` badges are tied to unlock/discovery style progress

### Badge progress storage

Badge state is stored in the scoped local key:

- `hrrra_badge_stats_v2_<playerId>`

The current player badge state is loaded, sanitized, mutated during play, and written back after relevant events.

### Badge reward flow

When a badge tier is unlocked:

- the reward queue is filled
- the badge reward overlay appears
- the player can step through multiple unlocks from the same run

The main overlay ids are:

- `badge-reward-overlay`
- `badge-reward-name`
- `badge-reward-tier`
- `badge-reward-trophy-base`
- `badge-reward-trophy-art`

### Badge stat updates

Badge stat mutations are done through helpers such as:

- `incrementBadgeLifetimeStat`
- `updateBadgeBestStat`

These are called from many gameplay events, for example:

- coins collected
- bags collected
- continues used
- lives lost or saved
- teleports
- jumps
- clean levels
- total score
- maximum speed

### Practical badge lookup rule

If you want to know why a badge changed, the fastest route is:

1. find the badge series in `BADGE_SERIES`
2. find the stat update helper that writes the underlying counter
3. search for the gameplay event that increments that stat

## 14. Mine System

The mine system is a small economy loop that fills storage over time.

### Mine state

The mine stores:

- current storage coins
- storage capacity
- upgrade level
- ad watch progress
- next coin time
- whether the short timer is unlocked

### Main storage helpers

Important helpers:

- `getMineStorageCoins()`
- `getMineStorageCapacity()`
- `getMineShortTimerMs()`
- `isMineShortTimerUnlocked()`
- `getMineStorageUpgradeMeta()`
- `transferMineStorageToWallet()`
- `syncMineStorageReminder()`

### Basic flow

1. coins are mined into storage
2. storage fills up to capacity
3. when full, mining pauses
4. transfer sends storage coins to wallet
5. mining resumes after transfer

### Storage upgrade flow

Storage can be upgraded multiple times.

The admin-configurable capacities are:

- `mineStorageCapacity`
- `mineStorageCapacityL2`
- `mineStorageCapacityL3`
- `mineStorageCapacityL4`

The shop upgrade uses ad watch progress and marks the item as sold when the maximum level is reached.

### Reminder flow

The Android reminder is synced from the mine transfer code.

When storage is transferred:

- the amount transferred is multiplied by the current interval
- the reminder worker is synchronized with the resulting delay

The reminder can also be canceled by calling the sync method with zero delay.

### Practical mine lookup rule

If the mine is behaving oddly:

1. inspect `economyStats`
2. inspect the storage capacity helpers
3. inspect `transferMineStorageToWallet()`
4. inspect the Android reminder worker if this is on mobile

## 17. Release and AAB Flow

The release flow is versioned and mirrored.

### What must stay in sync

- `android/app/build.gradle`
- `version-info.js`
- `version.json`
- Android public `version-info.js`
- Android public `version.json`

### Release principle

- every `.aab` prep must bump the release version
- Android public assets must mirror the same runtime metadata as the web root
- the release commit belongs on `main`
- the release commit is then pushed to `origin/main`

### Build output

The Android bundle is produced by Gradle and ends up as:

- `android/app/build/outputs/bundle/release/app-release.aab`

### Practical release lookup rule

If the store build or app version looks wrong:

1. compare the root and Android public version files
2. compare `android/app/build.gradle`
3. make sure the release commit was pushed from `main`
4. verify the app bundle was rebuilt after the bump

## 19. Data Flow And Save Lifecycle

The game uses a few recurring data lifecycles.

### Profile boot

At startup:

1. the game reads the active player id
2. it loads player skin progress
3. it loads badge stats
4. it loads economy stats
5. it loads admin and max score data as needed

The main entry point for this profile boot is:

- `loadPlayerSkinProgress(allowLegacyMigration)`

### Skin progress lifecycle

Skin progress is read from and written to:

- `hrrra_player_skin_progress_v2_<playerId>`

It contains:

- unlocked skins
- selected skin
- highest reached level
- Level X unlock state
- admin override flags for hard/full progression

### Badge lifecycle

Badge progress is:

- loaded from scoped local storage
- updated during gameplay events
- written back after relevant changes

### Economy lifecycle

Economy progress is:

- read from scoped storage
- updated when coins change
- written back after purchases, transfers, unlocks, and mine changes

### Admin lifecycle

Admin config is:

- stored globally for global toggles
- stored per level/mode/difficulty for mechanics tuning

The active config for a level is built from:

1. defaults from `config.js`
2. global overrides
3. mode-specific overrides
4. difficulty-specific overrides
5. level-specific overrides

### Max score lifecycle

Max score is stored per:

- player
- difficulty
- mode

It is updated when a run ends or when the admin reset section clears it.

## 20. Troubleshooting Paths

When a value is missing or stale, the following order usually finds the problem fastest.

### Screen content missing

Check:

1. `index.html`
2. the render function in `game.js`
3. `style.css`
4. the relevant asset path
5. `www/` or Android public mirror for stale copies

### Progress not saving

Check:

1. active player id
2. scoped storage key prefix
3. whether the write helper is called
4. whether the current profile is guest or authenticated

### Admin change not applying

Check:

1. whether the field is in `config.js`
2. whether the admin section includes the field
3. whether `saveGlobalAdminField` or `writeAdminStorageObject` is called
4. whether the runtime refresh function is called after the write

### Android reminder not firing

Check:

1. plugin registration in `MainActivity`
2. notification permission state
3. work request scheduling in `MineStorageReminderWorker`
4. whether the reminder was canceled by a later zero-delay sync

## 22. Screen Button Handler Map

### Storage reminder path

- The mine reminder is not a normal UI button path, but it still belongs in this map.

- The helper reaches the Android plugin bridge, which schedules or cancels the reminder worker.
